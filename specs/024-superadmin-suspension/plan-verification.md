## Implementation constraints for `/speckit-plan`

From the request, and kept out of the spec because they name classes:

- `User`, `ResolveTenant` and `TenantContext` do not change. `EnsureNotSuspended` (alias `not_suspended`) sets the in-memory `hotel` relation and never changes the `hotel_id` attribute.
- It skips the `null` scope, and runs one query on the normal path. Extra queries happen only for the replacement hotel, the account of a user with no hotels (both already in the NFRs) and the staff role (V3).
- `SkipIfHotelSuspended` reads the hotel through `HasHotel::hotelId()`. Suspension is written with `forceFill` by `App\Services\Superadmin\Suspension`.
- Impersonation is detected with `instanceof PersonalAccessToken` and `getAttribute('impersonator_id')`. No model strict mode is on, so this returns null until stage 5.
- On a repeat fixed reply, `replyFor()` returns null and `handle()` sets `THROTTLED`. That enum's comment says "per-sender rate limit" and needs updating.

## Checked and correct

- **Job lists**: the 21 classes `EntryPointDiscovery::queuedJobs()` finds split exactly into 3.9 (10), 3.10's loops and filters (6) and the exempt list (5, including `ProcessInboundWhatsAppMessageJob`).
- **`hotelId()` table**: each job has that property or record. `CreateAiInsightsJob` holds the user in an array, which `SerializesModels` doesn't touch, and a set `hotel` relation was confirmed to survive serialization, so it gets the current hotel.
- **Proactive flow**: the middleware runs before the claim, `failed()` only touches `SENDING` rows, so a blocked row stays `SCHEDULED`, and `EvaluateProactiveTriggersJob` redispatches due `SCHEDULED` rows. `valid_until` is checked in `ProactiveGuardrails`.
- **`MatchRecommendationOutcomesJob`** has a single-hotel path, which also needs `notSuspended()`. The other loops build on one `Hotel::query()`.
- **Middleware order**: `addToMiddlewarePriorityRelative` inserts each entry directly before `SubstituteBindings`, giving `ResolveTenant`, `EnsureFeatureEnabled`, `EnsureNotSuspended`, then binding.
- **Direct `hotel_id` reads**: no controller or policy reads the caller's `hotel_id` directly. `UserController:138` reads the target user's. Everything else reads `->hotel`, and only login and `GET /user` reload it.
- **Token issuers**: only `apiLogin` and `connect`. `/register` issues none. Six queued notifications match R11.
- **Alerts and Sentry**: `AlertOnRepeatedJobFailures` listens only to `JobFailed`, and `config/logging.php` has no Sentry channel, so the handlers' `Log::error` lines don't reach it. `QueueIntegration` pushes a scope per job, so the job's tag doesn't leak to the next one.
- **Stage 2 classes**: `DomainRuleException`, `EventLogger::recordPlatform`, `AccountIndexRequest`, `filterColumns()`, and the `Superadmin` controllers exist as the plan assumes. `HotelIndexRequest` doesn't, and is correctly marked Create.
- **Locale**: nothing calls `setLocale`. `lang/ar` exists, but only for calls naming a locale, so no `ar` file is needed. `UNAVAILABLE_REPLY` matches the design's text.

## Known limits

All left unchanged.

- **Validation before suspension on `PUT /api/hotel/{id}`**: `GenericUpdateRequest` runs before the controller body, so an invalid body gets `422` first. It reveals nothing new.
- **After reactivation**: skipped rebuild items, failed documents, imports, vouchers and guest notices stay as they ended, and guest memory extractions whose first job was skipped never run.
- **Fixed-reply limit**: a worker dying just after the send can send the reply twice. A guest's contact time is still recorded before the reply, as for any inbound message.
- **Plan numbering**: 3.3a and 3.4a are real items. Nothing is missing.
