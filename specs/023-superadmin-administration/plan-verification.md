## Known limits

All left unchanged, except the deleted-hotel entry, which the 2026-11-06 clarification changed.

- **Account owner's reach**: `HotelPolicy` uses `owner_id`, not group access, so an account owner can open only the hotels they own. New users can no longer be created without a home hotel (clarified 2026-11-06), so pairing and the tenant `UserController`, which use `hotel_id`, work for them.
- **Deleted hotel's staff (no longer left unchanged, clarified 2026-11-06, FR-015a)**: `accessibleHotelIds()` returns a soft-deleted `hotel_id` and pivot hotels, and `ResolveTenant` falls back to `$user->hotel_id` as the current hotel. Both must now skip soft-deleted hotels. WhatsApp and jobs for that hotel are not changed.
- **Shared rate limit**: `throttle:login` shares its buckets with `/login`, so reset attempts count against login attempts for the same email and IP.
- **Numbering**: the plan skips 2.8 and 2.9. Nothing else refers to them, so no work is missing.

## Verified as written

- `TenantContext::runForHotel(null, ...)` clears the current hotel, `withoutScope()` keeps it, and `BelongsToHotel` stamps an empty `hotel_id` from the current hotel. `event_log.hotel_id` is nullable and subjects are UUID morphs. `recordPlatform()` works as designed.
- Both tenant readers of `EventLog` exclude null-hotel rows for hotel users: `HistoryController` through the scope and `AiActivityController` through its `where`. `HistorySubjects` has no hotel, user or account type.
- `ResolvesModelFromRoute` throws for `AccountController`, so the `AccountIndexRequest` override is needed. `HotelController` and `UserController` resolve normally.
- `GenericQuery` reads `filter` from the request and `Filterable` adds an exact `WHERE`, so the account and hotel keys must be removed first.
- `MeteringService::recountSeats` writes counters and ignores the pivot, so `users_count` needs its own query. It will differ from the billing seat count for pivot-only users.
- `hotels.owner_id` is nullable, nothing else reads it apart from the policy and resource, and `HotelPolicy` needs it for CUJ 1's `GET /hotel/{id}`.
- `HotelPolicy` `create` and `delete` are called only from `HotelController`. `restore` and `forceDelete` have no callers.
- Removing `store` and `destroy` gives `405`, because `GET` and `PUT` remain on the same paths.
- The 2.14 test list includes every `POST` and `DELETE` caller of `/api/hotel`. `CreateUserTest:352` and `:454` are the right lines. Restore tests need rewriting, not only moving, because the rule changes from owner to account.
- New `super_admin` routes are covered by `crossTenantRuleFor`, and `/reset-password` is not a tenant route, so the only inventory change is removing the two entries.
- `password_reset_tokens` exists, `frontend_url` does not, and `throttle:login` keys on email and IP.
- CUJ 5 holds. Pairing codes are Sanctum tokens, so deleting tokens kills them. Deleting the device makes `devicePaired` false, and `ProcessInboundWhatsAppMessageJob::replyFor` returns `NOT_PAIRED_REPLY`.
- `POST /api/register` forces `role=admin`, and `PlatformSeeder` sets no hotel link. No CLI command creates super admins, so the seeder is the only source.
