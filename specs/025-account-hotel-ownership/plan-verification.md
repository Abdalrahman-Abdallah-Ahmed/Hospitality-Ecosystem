## Implementation constraints for `/speckit-plan`

From the request, and kept out of the spec because they name classes:

- `HotelPolicy::view` and `update`: `$user->isAdmin() && in_array($hotel->getKey(), $user->accessibleHotelIds() ?? [], true)`. Don't read `TenantContext`, which `EnsureNotSuspended` narrows. Don't use `allows()`, because it checks a record's `hotel_id` and hotels aren't in the permission enum. Update the `viewAny` docblock, which still mentions the hotel's owner.
- `HotelController::update` already refuses suspended hotels after authorization, so it needs only `owner_id` taken out of `PLATFORM_ATTRIBUTES`. Client-sent `owner_id` then drops out, because the generic rules cover only fillable columns.
- Registration: `Hotel::create` fills `hotel_group_id` through the `creating` hook, so read `$hotel->hotel_group_id` in the existing `$user->update`, inside the existing transaction. The new account can't already have an owner, so no catch is needed.
- Migration, next in sequence: drop `hotels.owner_id` with its foreign key, and add the composite unique index from V2, named `users_one_owner_per_account`. No backfill. A dev database holding two owners or a `group_admin` value has to be freshly migrated: the index would fail, and the cast would throw on read.
- `UserAdministration`: remove `claimOwnership` and `moveOwnershipWithRole`, keeping the `hotel_user` role sync in `changeAccess:143`. Clear `hotel_group_id` in `groupRoleAttributes`' null paths when the role was sent or the user held one. An employee with a link who never held a role and sends nothing stays as they are.
- With the column cast, tests asserting `->group_role` `toBe('owner')` need `GroupRole::OWNER`. `AccountUsageController:46`'s `! $user->group_role` becomes unreachable and can stay.

- Module access (V9, V19): `ChecksPermissions::allows` and 4 other policy checks compare with `$user->hotel`, as do `resolveHotel()` and about 40 call sites. So a middleware that sets that in-memory relation and narrows the scope to one hotel, for admins, moves them all, with no policy changes. WhatsApp is unaffected because it loads its own `User` (research R3, R9). Clarified 2026-11-07: `ResolveTenant` falls back silently on a header naming an unreachable hotel, which would put a create in the default hotel, so a request like that gets a plain `403` instead (FR-035a, V17). `SuspensionTest:336` and `DeletedHotelAccessTest:47` assert the old fallback and change.

## Checked and correct

- **Finding 3**: `HotelPolicy:37,45` requires `owner_id` while the list uses the tenant scope, so the list shows a hotel its record refuses.
- **Suspended flow**: for a user with other active hotels, `EnsureNotSuspended` narrows the scope, `Hotel` isn't tenant-scoped so binding still finds the hotel, the policy passes on the un-narrowed list, and `refusedAsSuspended` returns the suspended `403`. An unreachable caller stops at the policy first, and a user with only suspended hotels stops at the middleware. Using the narrowed scope would have returned a plain `403`, so the request's rule is right. A super admin's `null` scope skips both.
- **Widened access is what the request asks**: a second admin at a hotel can now change every setting there, including `whatsapp_number` and `is_active`.
- **Employees**: `isAdmin()` reads `users.role`, so an employee is refused even with a home hotel. `hotel_user.role` isn't involved.
- **Account on registration**: `Hotel::booted` creates a single-property group for any hotel without one, and the column is `NOT NULL`, so the account exists. `singlePropertyFor` always creates a new one.
- **`Hotel::admins()`**: includes anyone with a group role, read only by `CreationNotificationService`. Nothing depends on `group_admin`.
- **The `owner` relation**: never loaded in `app/`, so removing the relation and the resource key loses nothing else. No export, AI tool or other resource reads `owner_id`.
- **Finding an owner**: `UserIndexRequest` already allows filtering by `group_role`, and the frontend already filters users by account, so no endpoint is needed.
- **Hotel moves can't create two owners**: a move never writes a user's `hotel_group_id`, and refuses while home users hold one.
- **Account delete**: refused while hotels are live, and accounts aren't restored through the API, so a deleted account's owner row can't conflict.
- **Migrations and queues**: `owner_id` is defined only in `2026_07_18_000001`, with no later references. No queue, schedule or AI tool changes.

## Known limits

All left unchanged.

- **Employees in member hotels**: lists show those records, and opening one is `403`. It needs per-hotel staff roles and its own spec.
- **Ownerless gap during a swap**: two requests, with no owner between them. Nobody loses their own hotels.
- **An owner with no home hotel**: after the link is cleared they no longer resolve to an account, so a super admin can't add memberships until they have one. New users can't be created this way through the super admin API.
- **A direct link with no group role**: a user created with `hotel_group_id` alone still blocks a move. The API can clear it with `group_role: null`, but Manage access sends `group_role` only when it changes, so the UI can't.
- **Stage 6**: `DELETE /api/users/{id}` is the only way to delete a user, so stage 6 has to add a super admin route. Add it to that stage's inventory.
